# PocketPanel · 掌上面板
### 面向 Termux / ZeroTermux 的轻量服务器面板 · 设计方案 v0.1

> 定位：把闲置的 Android 手机 / 平板变成一台可远程管理的 Linux 小主机。
> 交互对标 **1Panel / 宝塔**，但底层为「无 systemd、默认非 root、ARM64、随时被杀后台」的环境重新设计。

---

## 1. 环境约束 → 设计取舍

这是整个方案的地基。很多面板移植到 Termux 上会失败，因为它们假设了桌面 Linux 的前提。

| 约束 | 现实问题 | 本方案对策 |
|---|---|---|
| **无 systemd** | `systemctl` 不存在，宝塔/1Panel 的服务管理直接失效 | 抽象 `ServiceManager` 三层适配：`runit`(termux-services) / `direct`(自研守护) / `proot`(容器内 systemctl) |
| **默认非 root** | 无法监听 80/443，无法 iptables | 面板默认端口 `1024–65535` 随机；root/ZeroTermux 提供「特权模式」解锁 80/443 与防火墙 |
| **Android 随时杀后台** | 面板进程静默消失 | `termux-wake-lock` + 常驻通知 + 电池优化白名单引导 + Termux:Boot 自启 + 自身看护（可选 root 下 `sv`） |
| **ARM64 / 无 glibc 部分场景** | x86 二进制、部分 pip 包无法用 | 纯 Python 标准库优先；需要编译的依赖走 `pkg install` 预编译包；v2 提供 Go 静态二进制 |
| **存储与 IO 受限** | 大量小文件扫描慢，eMMC 寿命 | 指标采样降频 + 环形缓冲 + 降采样存储；文件操作走异步任务 |
| **单用户设备** | 多租户是负担 | 单管理员 + 可选只读子账号；权限模型简化 |
| **随时断电 / 休眠** | SQLite 与任务状态易损 | WAL 模式 + 任务幂等 + 启动时任务恢复（标记 `interrupted`） |
| **无 80 端口** | Let's Encrypt HTTP-01 无法验证 | 默认 **DNS-01** 签发（Cloudflare/DNSPod/阿里云 API），或自签、或反代到有公网端口的机器 |

### 关键判断

- **不追求「全功能宝塔」**。手机上跑 MySQL + PHP + 面板，内存 2GB 就会 OOM。默认技术栈应是 **Nginx + PHP-FPM(按需) + SQLite**，MariaDB/Redis 作为可选组件按需启动。
- **面板自身必须极轻**。目标：空载内存 < 80MB，CPU < 1%，冷启动 < 2s。
- **移动端体验优先**。80% 的访问来自手机浏览器，桌面端是次要场景。PWA 必须支持。

## 2. 技术选型

| 层 | 当前实现 | 备注 |
|---|---|---|
| 后端 | **Python 3.14 + 标准库**（http.server / threading / subprocess） | 零第三方依赖，不装 FastAPI/Uvicorn |
| 存储 | JSON 文件 + 内存会话 | 单用户场景，SQLite 的收益低于引入复杂度 |
| 任务调度 | 线程 + 内存任务表 | 压缩/解压/下载/搜索/命令执行统一走同一套任务 |
| 系统采集 | `subprocess` 调 `top` / `df` / `ps` + `termux-api` | 不用 psutil（Android 上它读的 `/proc` 大多被拦） |
| 实时通道 | 轮询（3–15 秒） | 未做 WebSocket，单用户下收益不明显 |
| 终端 | 命令执行器（非 PTY） | 不支持 vim/top，见已知限制 |
| 前端 | **Vue 3.5 + Vite 6**，构建后静态托管 | 产物 gzip 后 52KB，设备端不需要 Node |
| 认证 | 内存 Session + HttpOnly Cookie | 24 小时，未做 JWT/TOTP |
| 打包 | 源码目录 + runit 服务 | 无 pip 安装步骤 |

> **为什么标准库而不是 FastAPI**：FastAPI 要装 starlette/pydantic/uvicorn 等一串依赖（几十 MB），换取的是自动文档与异步框架。单用户面板每天几百个请求，`ThreadingHTTPServer` 足够，且少一层依赖就少一类在 Android 上装不上的风险。

**内存实测**

| 组件 | 预算 | 实测 |
|---|---|---|
| Python 进程（含全部标准库） | 45–60 MB | **25.5 MB** |
| 采集器线程 | 5 MB | 含在上行 |
| 前端静态资源 | 0（浏览器侧） | 0 |
| **合计** | ≈ 60 MB | **25.5 MB** |

对照：Go 单二进制版为 5.4 MB。多出的 20 MB 换来 Python 生态与更短的迭代路径，在 5.6 GB 内存的设备上占 0.45%。

### 2.0 实现栈的三次变更

| 阶段 | 栈 | 结论 |
|---|---|---|
| 原型 | 单 HTML（无框架，ES5 兼容） | 用于验证交互，不适合长期维护 |
| 真机 v0.1 | Go 1.21 单二进制 + 单 HTML | 5.4MB / 启动 8ms，但前端是 1800 行无组件化的单文件 |
| 真机 v0.2 | **Python 3.14 + Vue 3** | 25.5MB / 启动 1s，前端 9 个单文件组件 |
| 真机 v0.3 | Python 3.14 + Vue 3 + **xterm.js** | 24.9MB / 启动 746ms，前端 141KB gzip（xterm 约 90KB），终端升级为真 PTY + SSH |

第二版把「单文件」当成了设计目标，这是错的：单文件只应服务于「运行时开销小」，而 Go 单二进制本身已经满足这一点，前端单 HTML 反而让 1800 行代码无法拆分复用。

第三版按运行代价重新选型：

- **后端换 Python**：设备实测 `pkg install python` 46 秒 / 45MB，加载全部标准库后 RSS 19MB，业务跑起来 25.5MB。相比 Go 多 20MB，可接受。
- **前端换 Vue 3**：构建在开发机做，设备端零 Node 依赖。组件化后拆成 9 个单文件组件：文件页 722 行（含模板），其余页面各 30–170 行，状态与渲染绑定，不再手写 DOM 操作。
- **API 保持完全一致**：36 个端点路径与 JSON 结构不变，两个版本共用 `data/` 目录，可随时切回。

v0.3 的增量只花在前端：xterm.js 让首次加载从 52KB 涨到 141KB（gzip），换来的是 ANSI 全屏程序、
光标定位、颜色、鼠标、触摸滚动全都由成熟组件处理，不用自己写一个转义序列解析器。
传输层加了 WebSocket（手写 200 行），保留长轮询作降级；两条通道共用 `seq`，切换时按序号续屏。
同期落地 M08 计划任务：`sched.py` 内置调度器（cron 解析 + 分钟刻度匹配 + 息屏补跑），
`messages.py` 收集后台事件，前端新增「计划」页与顶栏消息铃铛。
后端 PTY 部分约 500 行标准库代码，内存开销只在开会话时才产生（每会话一个读线程 + 256KB 缓冲）。
静态资源文件名带内容 hash 并配 `immutable`，升级后浏览器不会拿着旧 JS。

### 2.1 与宝塔 / 1Panel 的关键差异

不是「把宝塔搬到手机上」，而是同一套交互习惯、完全不同的底层假设。

| 维度 | 宝塔 / 1Panel | PocketPanel |
|---|---|---|
| 运行环境 | 完整 Linux + systemd | Termux，**无 systemd**，runit / 自研守护 |
| 权限 | 默认 root | **默认非 root**，特权模式可选 |
| 端口 | 直接监听 80/443 | 1024+，靠反代或隧道对外 |
| 数据库 | MySQL 常驻 | **SQLite 默认**，MariaDB 按需启停 |
| 面板体积 | 数百 MB | < 60 MB（不含运行环境） |
| 进程保活 | 不需要考虑 | wake-lock + 电池白名单 + Termux:Boot |
| 证书签发 | HTTP-01 | **DNS-01 优先**（无 80 端口） |
| 访问方式 | 桌面浏览器为主 | **移动优先** + PWA |
| 多用户 | 完整 RBAC | 单管理员 + 只读子账号 |
| 扩展方式 | 插件市场 | 脚本化应用商店 + 自定义应用 |

> 一句话：**把「服务器运维」降维成「设备运维」**。功能可以少，但每一步都必须在 4G 网络、6 寸屏幕、随时可能被系统杀掉的进程里跑得通。

### 3.1 服务管理适配器（核心设计）

Termux 下没有统一的服务层，是移植过程中最主要的兼容性风险。设计统一接口 + 三个实现：

```python
class ServiceAdapter(Protocol):
    def status(name: str) -> ServiceState: ...   # running/stopped/failed
    def start(name: str) -> None: ...
    def stop(name: str) -> None: ...
    def restart(name: str) -> None: ...
    def enable(name: str) -> None: ...           # 开机自启
    def logs(name: str, tail: int) -> AsyncIterator[str]: ...
```

| 适配器 | 探测条件 | 实现 | 适用场景 |
|---|---|---|---|
| `RunitAdapter` | `command -v sv` 且 `$PREFIX/var/service` 存在 | `sv up/down/status`、`sv-enable` | 原生 Termux 推荐 |
| `DirectAdapter` | 兜底 | 自建 `supervisor.py`：fork+setsid、写 pid、日志轮转、指数退避重启 | 无 runit / 自定义服务 |
| `ProotAdapter` | `command -v proot-distro` 且指定了发行版 | `proot-distro login <distro> -- systemctl ...` | 需要多 PHP 版本 / 完整 systemd |

> 面板启动时自动探测并选择，用户可在设置里强制指定。

### 3.2 异步任务模型

安装应用、备份、解压、目录统计这类操作用同步 HTTP 会超时，统一走任务队列：

```
POST /api/v1/tasks  →  { task_id }
GET  /api/v1/tasks/{id}          # 轮询（轻量，2s 间隔）
WS   /api/v1/ws/tasks/{id}       # 流式日志（推荐）
```

任务状态机：`pending → running → success | failed | canceled | interrupted`

`interrupted` 是移动端特有状态：进程被杀时任务没跑完，重启后面板扫描未完成任务并标记，避免前端永远转圈。

#### 5.3 关键设计决策

**回收站用 rename，不用复制。** 同一分区内 `os.Rename` 是元数据操作，几十 GB 的目录也能瞬间「删除」，不会出现「删一个 20GB 目录卡 3 分钟」。跨分区时才回退到复制 + 删除。

**版本快照有大小上限。** 只对 8MB 以下的文件做快照。超过的不快照，并在保存时明示「未生成版本」。否则编辑一个 500MB 的日志文件就能把磁盘写满。版本文件名用纳秒时间戳，同一秒内连续保存两次也不会排错序。

**搜索是异步任务，不是同步请求。** 递归搜索一棵大目录可能跑几分钟。做成任务后：8 秒软超时、200 条硬上限、到限即返回并标记 `truncated`，面板不会被一个搜索请求拖死。二进制文件读前 512 字节检测 `\0` 直接跳过，避免把图片当文本扫。

**分享只允许文件，不允许目录。** 目录分享会诱导用户暴露整棵目录树（可能包含 `.env`、密钥），且需要打包任务。要求先压缩再分享，语义更清楚。提取码错误 10 次锁定 10 分钟，防止 4 位码被穷举。

**压缩命令直接传参，不经过 shell。** `exec.Command("zip", args...)` 而不是 `sh -c "zip ..."`，文件名里的空格、分号、反引号不会被解释。这是 `exec` 与 `sh -c` 的安全分界。

**权限递归必须二次确认。** 对目录勾选递归时，弹窗明确写出「影响该目录下所有内容，可能上万项，且不可撤销」，确认后才执行。

#### 5.4 与备份（M11）的关系

回收站与历史版本都在 `data/` 下，**必须纳入 M11 的备份对象**，否则用户会以为「删了还能找回」，但备份里没有。

M11 实现时需要区分两种策略：

| 对象 | 默认 | 说明 |
|---|---|---|
| `data/trash/` | 排除 | 回收站本身就是「待删除」数据，备份它等于把垃圾一起备份；恢复时也不应把已删文件带回来 |
| `data/versions/` | 包含 | 版本快照是用户可能需要的，但体积可能较大，提供开关 |

这条约束写进 M11 的实现清单，避免两边各写一套。

**协议约定**：终端输入输出统一 base64。PTY 是字节流，UTF-8 多字节字符被轮询切在两段也不会乱码，
前端把 `Uint8Array` 直接喂给 xterm；若走文本会在分片边界出现半个汉字。

**传输：WebSocket 为主，长轮询兜底。** 同一会话两条通道共用 `seq`，切换时无缝续屏：

| | WebSocket | 长轮询 |
|---|---|---|
| 端点 | `GET /api/term/{id}/ws?since=N` | `GET /api/term/{id}/output?since=N&wait=20` |
| 静置 30 秒请求数 | 0 | 1 |
| 每帧开销 | 2–6 字节 | ~200 字节 HTTP 头 |
| 用途 | 默认通道 | 老浏览器 / 吞 Upgrade 的代理 |

`ws.py` 手写 RFC 6455（握手、文本/二进制/close/ping/pong、分片重组），约 200 行。
不引 `websockets` 的理由：`http.server` 是同步多线程模型，引异步库要么换掉整个服务器，
要么加线程/事件循环桥接，胶水比协议实现还长。一条连接两线程——读线程阻塞收帧，
主线程挂在会话 Condition 上等 PTY 输出（出字即推，不轮询），共用一个写锁防帧交织。
实测 3 条连接 +6 线程，关闭后线程数与 RSS 完全回落。

握手必须校验 `Origin` 与 `Host` 同源：WS 不受 CORS 约束且 Cookie 自动携带，
不校验的话用户打开任意恶意页面就能连到局域网面板（CSWSH）。

降级策略：`auto` 模式下 5 秒没 `open` 或 `onclose` 触发就退回轮询；设置页可强制 `ws` / `poll`；
状态栏实时显示当前通道。断线后先退回轮询保证可用，WS 下次进入页面时再尝试。

清单托管没有变（Cloudflare Worker + KV），三级降级（远程 → 缓存 6h → 内置）也没有变。

**清单上架结果（2026-11-01）：报了 18 个，最后只留 11 个**

| 保留（真机装过、首页打开过） | 撤下（真机跑不通） |
|---|---|
| Nginx、OpenList、Syncthing、Navidrome、Gitea、Redis、Uptime Kuma、Memos、Vaultwarden、Gotify、Alpine | FileBrowser、n8n、RSSHub、Grafana、PostgreSQL、Linkding、MeTube |

**2026-11-07 追加 New API（第 12 个，`verified: true`）**：AI 模型统一网关，
镜像 `calciumion/new-api:latest`，默认端口 3002，`/data` 单目录持久化。
判断它能跑的依据不是猜，是三层实证：

1. **二进制**：解出 arm64 层后 `file` 显示 `statically linked`，无解释器、
   无动态依赖，也不 fork 子进程——Android 上最容易出事的环节它都不碰。
2. **入口**：`ENTRYPOINT ["/new-api"]`，没有 tini、没有 supervisor，
   正好绕过前两类坑。
3. **真机**：Android 10 / aarch64（华为 BLA-AL00，Termux）上用 udocker
   跑通全流程——冷启动 902ms、首页 200（3ms）、管理员初始化、登录、
   渠道/令牌接口全 200；杀掉重启 685ms，`system is already initialized`，
   SQLite 数据完好；常驻 RSS 42MB。

同时复现了「`udocker create` 报 extracting image layer、但 ROOT 已解完」的
已知坑，`proot ... run` 直接起来——印证了面板以容器目录为准的判断是对的。

撤下来的原因分三类，都不是配置问题：

1. **tini 入口**（FileBrowser / n8n / RSSHub）——它要当 PID 1，proot 里做不到，
   直接 `tcsetpgrp failed` 或 `exec failed`。构建成功、容器创建成功都不代表能跑。
2. **proot 没实现的系统调用**（PostgreSQL `shmget`）——无解。
3. **网络与体积**（Grafana / MeTube）——手机上拉几百 MB 镜像反复超时；
   n8n 解压后 1.4G，就算能跑也不适合塞进兜里的机器。

清单因此单独放到 `catalog.py`：它是唯一真相源，`appstore-worker/seed/catalog.json`
由 `sync_seed.py` 单向生成，测试逐条比对防漂移。加一个应用只改这一处，
但**上架前必须真机装一遍**——`verified` 字段写的是实测结果，不是信心。

> **易错点：`*/N` 的计时起点是分钟刻度，不是创建时刻。**
> 「每 N 分钟」生成 `*/N * * * *`，其触发点是系统分钟刻度（00、05、10…），**不是从点击「添加任务」那一刻开始倒计时**。14:07 创建「每 5 分钟」，首次执行是 **14:10**，而非 14:12。原因在于 cron 的 `*` 表示「每个取值」而不是「从现在起的 N 分钟后」，`*/5` 的真实语义是「能被 5 整除的分钟数」。
> 需要固定偏移时必须手写表达式，例如 `17 * * * *`（每小时第 17 分）、`17 */6 * * *`（每 6 小时的第 17 分）。
> 产品上的对策：简易模式的输入框下方直接展示触发点序列（00、07、14、21…），列表页顶部固定一条说明，避免用户按「相对时间」理解。

>

### M15 内网穿透（独立一级模块）

> 由原 M10 的 10.2 提升而来。功能量、交互闭环与安全边界都足够独立，且横跨创建、启动、保活、对账、配额展示多个环节。
>
> **定位**：把「服务暴露到公网」抽象成统一能力。用户不关心底层是 frpc、cloudflared 还是 tailscale，只关心三件事——**有没有能访问的地址、它稳不稳、流量还剩多少。**

#### 15.1 边界

| 做 | 不做 |
|---|---|
| 统一隧道视图，FRP / Cloudflare / Tailscale / ngrok / 自定义同一套状态语义 | 内置 FRPS 服务端（应部署在有公网 IP 的 VPS，手机做服务端无意义） |
| 全托管创建：选服务商 → 填凭据 → 一键建隧道拿地址 | 复刻 frp 官方 dashboard |
| 半托管：粘贴配置或上传文件，面板只管客户端进程 | 默认暴露面板管理端口（安全红线） |
| 纯本地：填 FRPS 地址 + token，自建节点 | 内置公共 FRPS 推荐（稳定性与合规风险不可控） |
| 多格式配置导入、按版本生成、按客户端校验 | 容器化穿透编排（与 M07 解耦） |

#### 15.2 三层抽象

```text
Provider 层（隧道从哪来）   Preset 层（免凭据模板）   Client 层（本机怎么跑）
SakuraFrp / OpenFrp         FreeFrp（内置）           FrpcClient / CloudflaredClient
Cloudflare / Tailscale      自建 FRPS 模板            TailscaleClient / NgrokClient
ngrok / Manual                                        GenericCommandClient
        │                        │                          │
        └────────► TunnelConfig（归一化）◄──────────────────┘
                              │
                渲染 → 三层校验 → 落盘 → ServiceManager 启动
```

```python
class TunnelProvider(Protocol):
    kind: str
    capabilities: ProviderCapabilities
    def test_connection(self) -> ProviderStatus: ...
    def list_nodes(self) -> list[Node]: ...
    def create_tunnel(self, spec: TunnelSpec) -> RemoteTunnel: ...
    def get_status(self, remote_id: str) -> RemoteStatus: ...
    def get_traffic(self, remote_id: str) -> TrafficStats: ...
    def list_remote_tunnels(self) -> list[RemoteTunnel]: ...   # 对账用

class TunnelClient(Protocol):
    kind: str
    def detect_binary(self) -> BinaryInfo | None: ...
    def validate_config(self, cfg: TunnelConfig) -> ValidationResult: ...
    def render_config(self, cfg: TunnelConfig) -> str: ...
    def start(self, inst: TunnelInstance) -> None: ...
    def status(self, inst: TunnelInstance) -> ClientStatus: ...
    def public_urls(self, inst: TunnelInstance) -> list[str]: ...
```

**关键设计**：Provider 返回的 `RemoteTunnel`、Preset 展开的模板、用户粘贴的配置文件，都先归一化为 `TunnelConfig`，再进入同一条下游链路。「API 创建」「选预设」「手填配置」不是三套代码。

**Preset 与 Provider 的区别**：Preset 只是一组预填参数（serverAddr / serverPort / token / 端口范围），不涉及远端 API，因此**没有 API 改版风险**。FreeFrp 属于这一类。

**能力矩阵**：Provider 用 `ProviderCapabilities` 声明能否建隧道、删隧道、查流量、列节点、绑自定义域名。UI 按能力渲染——`create_tunnel=False` 时创建向导自动跳过「远端创建」进入粘贴模式；`get_traffic=False` 时流量卡显示「服务商未提供」，不显示假数据。

#### 15.3 三种接入模式与降级

| 模式 | 用户操作 | 底层行为 | 适用 |
|---|---|---|---|
| **full 全托管** | 选服务商 → 填 API Key → 测试 → 选服务 → 选节点/域名 → 一键创建 | Provider 建隧道 + Client 落盘启动 | SakuraFrp / OpenFrp / Cloudflare |
| **semi 半托管** | 粘贴配置 / 上传文件 / 填 token → 预览 → 启动 | 仅 Client 管理 | 无 API 的服务商、已有隧道、旧机迁移 |
| **local 纯本地** | 填 FRPS 地址 + token + 端口 + 类型 | 仅 Client 管理 | 自建 FRPS / 自建 cloudflared |

**降级规则（必须写进代码）**：

```text
Provider API 失败
  ├─ 凭据过期 / 权限不足  → 提示重新授权，隧道保持运行
  ├─ 限流 / 5xx          → 指数退避重试 3 次，标记 provider_degraded
  ├─ 服务商改版 / 404     → 标记 provider_incompatible，自动切半托管
  └─ 远端隧道不存在       → 标记 orphaned，提示「本地配置仍在，可继续运行或重建」
任何降级状态下：已落盘配置不删、进程继续保活、UI 明示「服务商失联，隧道仍在本地运行」
```

这条是接入越多服务商越重要的保险丝。没有它，一个服务商改 API 就能让用户所有隧道不可用。

#### 15.4 配置体系（本模块的核心复杂度）

**格式与版本映射**：frpc ≥ 0.52 用 TOML（默认）/ YAML / JSON，INI 仅用于 ≤ 0.51 的导入与生成。生成前读取二进制版本决定格式，检测到旧版本时格式选择器只给 INI 并提示升级，新版本则把 INI 置灰。

**raw / structured 双模式——同一时刻只有一个可编辑入口**：

| 模式 | 真相源 | 表单 | 文件预览 | 切换 |
|---|---|---|---|---|
| `structured` | 表单 | 可编辑 | 只读（派生产物） | 可切 raw，生成文件 |
| `raw` | 配置文件 | 置灰 | 可编辑 | 可切 structured，解析填表并**明确告知注释丢失** |

raw 是兼容现实配置的逃生口，也是 Provider 降级后的兜底。没有它，用户从服务商后台复制的配置、旧机器迁移来的配置、教程里抄来的配置都进不来。

**三层校验**：

| 层 | 内容 | 失败表现 |
|---|---|---|
| 语法层 | 解析器报错 | 行号 + 列号 + 原文片段，编辑器标红 |
| Schema 层 | 必填缺失、类型、端口范围、type 枚举、端口冲突 | 定位到具体 key |
| 权威层 | `frpc verify -c <tmp>` | stderr 原样返回，这是唯一能保证「服务商能连上」的校验 |

**多 proxy**：一个配置文件可含多个 `[[proxies]]`，列表按「实例组」展示，展开见条目；启停作用于整个 frpc 进程，删除时提示「将同时停止 N 个代理」。

**敏感信息**：token / secretKey / 插件密码默认打码，日志正则脱敏，配置文件权限 600，目录 700。解析用 `tomllib` 与 `yaml.safe_load`，禁用危险标签。

#### 15.5 保活、拨测与对账

```text
进程层  DirectAdapter 指数退避 1s→2s→4s→…→60s，连续失败 10 次标记 failed
客户端层 frpc admin API / cloudflared metrics 每 30s 轮询，异常则重启
远端层  每 60s 拨测 public_url，连续 3 次失败告警「公网不可达」，恢复后发恢复通知
凭据层  token 7 天内过期提醒；失效标记 provider_degraded，本地继续跑
网络层  复用 10.9 全局网络切换事件，切换后触发 sync + 拨测
对账层  每 10 分钟 sync()，识别 orphaned / remote_only / drifted 三态
```

告警全部复用 M09，事件类型：`tunnel_down`、`tunnel_unreachable`、`tunnel_flapping`、`tunnel_orphaned`、`tunnel_quota`、`provider_degraded`、`token_expiring`。

##### 15.5.1 网络变动的智能恢复（已落地）

「网络切换后触发 sync + 拨测」这一层是 **Client 层** 的事，和 Provider / 对账无关。
手机上网络一变（WiFi ↔ 4G、电梯断信号、DHCP 换 IP），长连接必断，但**客户端不一定能自己爬起来**——
有些能，有些不能。面板的做法不是"猜"，是**去问客户端自己**。

```text
网络变动 ──▶ 防抖 45s ──▶ 二次确认 ──▶ 逐个探测 ──▶ 只重启真正掉线的那个
   │                                        │
   │                                        └─ 探测不了 → 跳过，不动
   └─ 45s 内又变 → 重置计时
```

**防抖**：IP 或网络类型一变不立刻动作，起 45 秒计时器（可配 30–60 秒）。
期间 IP 再变就重置计时。计时到期后**再调一次接口**确认当前确有 IP、确非断网，才进入恢复。
二次确认不能省——到期那一刻网络可能刚好又断了，这时去重启只是把坏状态固化。

**探测**（两种客户端两套问法，实测核对过 frpc 0.71.1 / cloudflared 2026.10.6）：

| | frpc | cloudflared |
|---|---|---|
| 端点 | `http://127.0.0.1:{webServer 端口}/api/status` | `http://127.0.0.1:{metrics 端口}/ready` |
| 端口来源 | 配置里的 `webServer`；没有则面板按实例 id 派生分配（17400 起） | 命令行注入 `--metrics 127.0.0.1:{端口}`；不指定时在 20241–20245 随机挑，多实例无法区分 |
| 健康 | 返回含代理项且 `status` 为 `running` | HTTP 200 且 `{"status":200,"readyConnections":N}`，N > 0 |
| 不健康 | 断开时整体返回 `{}`；代理 `status` 为 `offline` | `/ready` 连不上，或 `readyConnections` 为 0 |

**三态处理**是安全底线：

| 探测结果 | 动作 |
|---|---|
| 健康（客户端自己重连成功了） | **不动它**——进程一直在跑，重启反而掐掉刚建立的连接 |
| 不健康（确实掉线） | 只重启这一个实例 |
| 探测不了（没端口 / 401 / 不支持） | **跳过，不动** |

第三种最关键：把"探测端点没配好"当成"客户端坏了"，就会重启动一堆本来活得好好的隧道，
**退化成粗暴全局重启**——这是需求明令禁止的。

> **实现取舍与踩坑**：
>
> - **frpc 不支持 `include` 指令**（实测 `json: unknown field "include"`），没法用 include 注入
>   `webServer`。改用运行时配置文件 `{id}.run.conf`（用户原文 + 追加 `[webServer]` 段），
>   **用户在面板里看到的配置永远是自己写的那份**，零污染。
> - **frpc 的 `webServer` 只认 `user` / `password`**，不支持 `webServer.auth.token`
>   （实测 `json: unknown field "auth"`）。webServer 返回 401 时按"探测不了"处理，跳过。
> - **`/api/status` 的结构与直觉不同**：按协议分组（`{"tcp":[...]}`）而不是 `proxies` 列表，
>   status 值是 `running` 不是 `online`。实现里遍历所有 list 类型的值收集代理项，
>   判定时 `running` / `online` 都接受。
> - **cloudflared 的 `/ready` 里没有 "Ready" 字样**，返回的是 `{"status":200,"readyConnections":4,...}`。
> - **基线必须即时更新**：IP 变化后若不立刻更新基线，下一轮 10 秒轮询又会判定"又变了"，
>   计时器被反复重置，45 秒永远走不到。这是实测发现的真实 bug。
> - **熔断阈值语义是"允许的次数"**：`circuit_max=3` 表示允许重启 3 次，第 4 次被拦下并告警，
>   判定用 `>=` 而非 `>`。
>
> **网络识别**（Termux 真机）：优先用 `termux-wifi-connectioninfo`；但真机**没有 `ip` 命令**，
> 只有 `ifconfig`，且 `termux-telephony-deviceinfo` 需要 `READ_PHONE_STATE` 权限（不可用），
> 所以蜂窝识别靠**接口名匹配**（`rmnet*` / `cc*` / `ap*` / `pdp*` / `wwan*` / `usb*` / `rndis*`）。
> **蜂窝优先于 WiFi**——切到 4G 时 WiFi 那份数据可能还是旧值。

**熔断**：5 分钟滑动窗口内同一隧道因网络变动重启超过 3 次 → 暂停该隧道的自动恢复，
推送告警「网络频繁闪断，已暂停自动重连，请检查网络环境」，面板上提供手动解封。
避免网络反复闪断时进入无限重启的死循环。

**前端提示**：事件经 WebSocket（`/api/events/ws`）推送，顶部横幅四态：

| 事件 | 时机 | 横幅 |
|---|---|---|
| `network_changed` | 触发防抖 | 「检测到网络切换，正在等待网络稳定（45s）...」+ 倒计时 |
| `network_recovered` | 恢复结束 | 「网络已恢复，X 个隧道正常，Y 个隧道已重启」 |
| `network_circuit_broken` | 熔断触发 | 「网络频繁闪断，已暂停自动重连，请检查网络环境」（红） |

WS 事件通道额外接受 `?token=` 查询参数：浏览器的 WebSocket API 不能自定义请求头，
只靠 cookie 在代理 / 跨站策略下会失效，事件就收不到了。两种方式等价，都是面板 session token。

| 问题 | 现象 | 对策 |
|---|---|---|

### M16 消息盒子

> 全局常驻组件，不属于任何单一模块。任务来源横跨 M03 / M04 / M05 / M07 / M08，通知来源横跨 M09 / M12 / M15。

**定位**：把「异步任务」和「系统通知」收敛到一个入口。用户点开就知道三件事——**现在在跑什么、跑到哪一步、刚刚发生了什么**。

#### 16.1 两个分栏

| 分栏 | 内容 | 生命周期 | 排序 |
|---|---|---|---|
| **任务** | 安装应用、备份、解压、证书签发、站点部署、批量文件操作 | 进入终态后保留 7 天，可手动清理 | 运行中置顶，其余按时间倒序 |
| **通知** | 告警、安全事件、证书到期、配额提醒、版本更新、任务完成 | 保留 30 天，可标记已读 | 未读置顶 + 时间倒序 |

角标 = 未读通知数 + 进行中任务数。任务完成时自动生成一条通知，可在设置里关闭，避免「装个软件收两条消息」。

#### 16.2 任务状态机

```text
pending ──► running ──► success
              │  │
              │  ├──► failed ──► (retry) ──► 新 task
              │  └──► canceled
              └──► interrupted   # 进程被杀，重启后标记
```

`interrupted` 是移动端特有状态。Android 杀掉面板进程时，正在跑的任务不会留下正常终态；面板重启后扫描 `running` 且无心跳的任务，统一标记为 `interrupted`，避免前端永远停在 99%。

#### 16.3 实时性

| 机制 | 说明 |
|---|---|
| 日志缓冲 | 每个任务在内存保留最近 500 行，落盘保留完整日志 |
| 推送 | `WS /ws/tasks` 推送 `{id, progress, line}`，前端增量追加，不整页重绘 |
| 断线重连 | 重连后先拉 `GET /tasks?status=running` 快照，再订阅增量，避免丢行 |
| 自动展开 | 打开面板时自动展开第一个运行中任务的日志，无需再点一次 |
| 滚动策略 | 日志区仅在「原本就在底部」时自动跟随，用户上翻查看历史时不打断 |

#### 16.4 交互约束

- **取消**：先发 `SIGTERM`，10 秒未退出再 `SIGKILL`；已产生的中间文件保留，由用户决定是否清理。
- **重试**：创建新 task 并复用原参数，不复用旧 task id，历史日志保留。
- **通知跳转**：点击通知标记已读并跳到对应模块（安全事件 → 安全页，证书 → 网站页，配额 → 内网穿透）。
- **批量已读**：只影响通知，不影响任务。

- **形态**：桌面端右上角浮窗（440px），移动端全屏面板。移动端不做浮窗，因为 6 寸屏上的浮窗既挡内容又难点。

#### 15.8 内置预设：FreeFrp（公益）

FreeFrp（`freefrp.net`）是国内运营的公益 FRP 服务。经核实：**没有账号体系、没有 API、没有控制台**，隧道完全由客户端配置文件决定，认证 token 是公开固定值。因此它不是 Provider，而是 **Preset**——面板预置服务器参数，用户只填本地端口与域名。

| 项 | 值 |
|---|---|
| serverAddr | `frp.freefrp.net` |
| serverPort | `7000` |
| auth.token | `freefrp.net`（公开固定值，无需申请） |
| 服务端版本 | 0.56.0（TOML，≥ 0.52 分界） |
| HTTP / HTTPS 入口 | 80 / 443 |
| TCP / UDP 端口范围 | 10001–50000 |
| 免费子域名 | **不支持**，HTTP 必须自有域名并 CNAME 到 `frp.freefrp.net` |
| 额度承诺 | 无公开 SLA，属公益资源 |

**接入方式**：`mode = local`，走 Preset 展开，不经过任何远端 API。这是可靠性最高的接入形态——服务商无法通过改接口让你的隧道失效。

**三条必须处理的限制**：

1. **HTTP 需要自有域名**。没有域名时，向导不应给出一个假的免费地址，而应直接推荐 TCP，并说明「如需域名访问，请先在 DDNS 中绑定」。
2. **remotePort 全局唯一**。端口被占用时 frpc 会报 `port already used` 并退出。面板的自动化流程是：从 10001–50000 随机取端口 → 启动 → 监听 stderr → 命中冲突则换端口重试，最多 5 次、间隔 1.5s。若 5 次都失败，回退到手动指定并提示「当前时段端口紧张」。
3. **公益资源无可用性承诺**。隧道卡片标注「公益」徽标；公网拨测连续失败时，文案优先提示「FreeFrp 服务可能繁忙」，而不是笼统报「隧道故障」，避免用户误判为本地配置错误。

**为什么不包装成「全托管」**：它没有 API 可调。硬做成托管，UI 就会承诺做不到的事（自动建隧道、查流量、列节点），用户点下去发现不一致，信任成本比一开始就说明更高。

> 预设不是硬编码在 UI 里的字符串。它存放在 `presets.yaml`，允许用户自定义新的公益节点或自建模板，字段与内置项一致。

#### 15.9 安装时自动创建隧道

应用安装（M07）与建站（M03）都可以勾选「同时创建内网穿透」，避免装完再跑去配置一遍。

**开关的默认值**来自 M15 设置，而不是每次都问：

| 设置项 | 默认值 | 说明 |
|---|---|---|
| 新应用默认自动穿透 | 关 | 打开后安装向导的勾选框默认勾上 |
| 默认服务商 | FreeFrp（公益） | 也可选自建 FRPS 或其他 |
| 默认类型 | TCP | HTTP 需要域名，不适合做默认 |
| 域名后缀 | 空 | 配置后自动生成 `应用名.后缀` |
| 失败策略 | 跳过并提示 | 可选「阻止安装」或「重试」 |

**执行顺序**：安装任务 → 探测本地端口 → 创建隧道 → 启动客户端 → **把访问地址回填到安装完成的通知与站点详情**。

失败时不回滚已安装的应用，只把隧道标为 `failed` 并在消息盒子给出重试入口——应用装好了却因为穿透失败而回滚，代价太大。

### M17 容器运行时（独立一级模块）

**定位**：基于 udocker / udockerd 的**无 root 轻量容器运行时**，目标是「兼容 Docker 镜像生态的受限容器管理」。
不是完整 Docker 管理器——不引入 QEMU、Podman，也不做任何需要 root / cgroups / namespaces 的能力。

**为什么值得做**：Android 上装不了 Docker，但大量自建服务（nginx、redis、frps、数据库）只有 Docker 镜像。
udocker 用 PRoot 把镜像 rootfs 跑起来，能让这批镜像在手机上可用；代价是必须放弃 Docker 的一半能力。
所以这个模块的第一设计原则是**先把不能做的事说清楚**，而不是先堆功能。

#### 17.1 架构

| 层 | 实现 | 职责 |
|---|---|---|
| 前端 | `views/Docker.vue` | 能力边界常驻展示、容器/镜像/编排三页、创建表单、目录选择、日志、详情 |
| 适配层 | `runtime.py` | ContainerRuntimeAdapter：能力声明、参数校验、异步任务、事件监控告警 |
| 协议层 | `dockerclient.py` | Docker Engine API 客户端（标准库实现，零第三方依赖） |
| 守护层 | `udockerd.py` | Engine API v1.41 子集，翻译成 udocker 命令并托管容器进程 |
| 托管层 | `svc.py` | runit / 直管双适配器，启停保活、开机自启、日志、面板重启后接管 |
| 编排层 | `compose.py` | docker-compose 子集解析（手写 YAML + .env 插值 + 拓扑排序） |

面板**只通过 Engine API 与运行时通信**，不直接拼 udocker 命令。好处是任何标准 Docker 客户端
都能直连 `tcp://127.0.0.1:2375`，面板自身也可被替换。

#### 17.2 能力边界（UI 常驻四条 + 两条补充）

| 边界 | 真实约束 | UI 表达 |
|---|---|---|
| **网络恒为 host** | 无 bridge、无容器间隔离、端口映射语义退化为「直接监听宿主机端口」 | 顶部常驻卡片 + 创建表单端口区标注「仅作记录与校验」 |
| **无 cgroups** | CPU / 内存无硬限制，配额滑块没有任何落点 | 常驻卡片；不渲染任何资源配额控件 |
| **无 Volume 对象** | `docker volume` 恒为空，持久化只靠 bind mount | 常驻卡片；映射区文案「目录映射，非 Docker Volume」 |
| **无 BuildKit / 无构建** | udocker 1.3.x 没有 build 子命令 | 常驻卡片；镜像页提供「导入 docker save 产物」 |
| 端口 < 1024 不可监听 | 非 root 绑不上 | 创建时后端拦截 + 前端提示 |
| bind mount 的 `ro` 无法强制 | PRoot 不拦写系统调用 | 只读选项标「仅标注」，详情页给 warning |

「不隐藏」是硬要求：这四条**不折叠、不藏进帮助文档**，直接排在页头下方，用户滚不走。

#### 17.3 分层实现

| 阶段 | 内容 |
|---|---|
| **P1** | 镜像拉取（指定 ARM64）/ 列表 / 删除；容器列表（运行中/已停止）、启停重启删；日志 tail；**exec 进容器复用 Web 终端**；创建表单（镜像/名称/命令/环境变量/bind mount/端口 ≥1024/重启策略 no·always·on-failure） |
| **P1.5** | 镜像导入（兼容 `docker save`，走 `udocker load`）；bind mount 目录选择器（宿主机路径限制在 `$HOME` 内）；容器详情（状态、启动时间、host 模式 IP、挂载列表、环境变量敏感值打码） |
| **P2** | compose 子集一键起（导入 yml、`depends_on` 拓扑、restart、`.env`，标注「非原生 Compose」）；执行模式 P1/P2/F1 切换；容器异常退出 / 频繁重启接入 M09 告警 |

**执行模式**：`P1` PRoot + seccomp（默认）、`P2` 关加速（老内核更稳）、`F1` Fakechroot（更快，依赖内核与 libfakechroot）。
建容器时选，切换需重建。

#### 17.4 明确不做

资源限制、自定义网络/隔离/高级端口映射、Volume 对象管理、BuildKit/多阶段构建、
Swarm/K8s/完整 Compose、QEMU 模拟 x86、把 udocker CLI 当作主要集成方式。

理由统一：这些能力要么需要 root/cgroups/namespaces，要么需要 QEMU 做指令翻译（手机性能不可接受），
做出来只会是一个「看起来能点、点下去报错」的入口。

#### 17.5 关键实现取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| docker-py vs 自实现客户端 | 自实现 `dockerclient.py`（400 行） | 项目硬约束是后端零第三方依赖；协议实现完整，不牺牲互操作性 |
| exec 怎么进容器 | `udocker run <容器> <shell>` + Engine API 劫持 | udocker 1.3.x 没有 exec 子命令；host 网络下体感接近 `docker exec` |
| 容器状态存哪 | `udockerd` 的 `state.json`（0600） | 唯一真相源；面板重启后按 pid + cmdline 校验接管 |
| 进程判活 | 读 `/proc/<pid>/stat` 看 `Z` 位 | 僵尸进程下 `kill(pid,0)` 仍成功，只看它会永远显示「运行中」 |
| 手动停止要不要告警 | 不要（`manual_stop` 标记） | 用户点的停止不是异常，否则每停一次报一次警 |
| 事件流断了怎么办 | 每次连上按状态补一次账 | udockerd 的事件缓冲只在内存（300 条），守护进程一重启就清零；只靠事件必然漏报 |
| 补账怎么不误报 | `inspect` 暴露 `PocketPanel.ManualStop` | 手动停止的容器在重连时也是 `exited`，不带这个标记会被当成崩溃重报一遍 |
| 两条告警的节流 | 分开算，不串联 | 容器每几秒崩一次时，第一条「异常退出」会一直占着 5 分钟冷却，重启告警就永远发不出来 |
| 长连接多久重建 | 30 秒 | 改了 Engine API 端口 / 换了守护进程实例能及时生效；重连按水位续上，不丢事件 |
| 路径安全 | `core.sandbox()` + 拒绝面板数据目录 + 拒绝整个 HOME | 面板数据里有密码哈希与隧道 token，映射进容器等于送出去 |

#### 17.6 验收

1. udockerd 能被 ServiceManager 启停保活，面板重启后自动恢复；
2. 能拉 ARM64 镜像并启动 alpine 类容器，能看日志、进终端；
3. 端口 < 1024 被拦截且给出可读原因；
4. bind mount 宿主机路径经沙箱校验，不允许越权目录；
5. UI 明确展示 host 网络、无资源限制、无 Volume 对象、无 BuildKit 四条边界；
6. 容器异常退出能触发 M09 告警，守护进程/面板重启换出来的空窗也要补上；
7. 移动端容器列表与创建表单单手可完成，触控目标 ≥ 44×44px；
8. 不出现任何需要 root 或依赖 cgroups/namespaces 的功能入口。

### M16 AI 网关（独立一级模块）

> **编号说明**：需求文档把 AI 网关定为 M16；本文档原有的 M16「消息盒子」功能已实装
> （`messages.py`），两者编号撞车。落地实现与 README 一律称「AI 网关（M16）」，
> 消息盒子在功能上不受影响，只是文档里两个 M16 并存。

**定位**：**轻量大模型 API 聚合与转发网关**——统一管理各厂商 Key，对外只暴露一套接口，
四种主流协议都能进能出。不是任何场景化 AI 功能：没有「读日志自动诊断」、
「根据终端输出现场生成配置」这类花哨入口。

**为什么值得做**：手机上的 AI 客户端（LobeChat、Cherry Studio、各种脚本）各自只认一种协议，
厂商 Key 又散落在好几个 App 里。用户要的是「一个地址、一个 Token、四种协议都能用」，
而不是每个客户端填一遍 Key。

**边界的第一原则同样是「先把不能做的事说清楚」**。

#### 16.1 架构

| 层 | 实现 | 职责 |
|---|---|---|
| 前端 | `views/Gateway.vue` | Provider 管理 / 对话测试 / 用量统计三页签 |
| 路由层 | `gateway.py` | Provider 存储、模型路由、透传与转换的分流、限额、断连、用量 |
| 转换层 | `gateway_ir.py` | 四协议 ↔ IR 中间表示，请求 / 响应 / 流式三层编解码 |
| 密钥层 | `secretbox.py` | `secret.key` 生成、HMAC-CTR + EtM 加解密、掩码 |
| 宿主 | `app.py` | `/v1*` 走独立原始流式通道，`/api/ai/*` 走面板 session 管理接口 |

面板**后端零第三方依赖**这条硬约束在这里最难受——FastAPI 装不进 Termux，
httpx 也装不上。所以用 `http.server.ThreadingHTTPServer` + `http.client` + `ssl` +
`sqlite3` + `hmac` 全部标准库实现，等价映射：

| 想要的语义 | 实际实现 |
|---|---|
| `await request.body()` | 禁止；改用 `BodyReader` 逐块读 |
| `request.stream()` | `BodyReader.iter_rest()` 生成器 |
| `httpx.AsyncClient` | `HTTPConnection` + `http.client` |
| `request.is_disconnected()` | `ClientWatch`：`select` + `MSG_PEEK` 判断开 |

#### 16.2 四协议与 IR

| 协议 | 网关入口 |
|---|---|
| OpenAI Chat | `POST /v1/chat/completions` |
| OpenAI Responses | `POST /v1/responses` |
| Anthropic | `POST /v1/messages` |
| Gemini | `POST /v1beta/models/{model}:generateContent`（流式 `streamGenerateContent?alt=sse`） |

跨协议转换不能靠字符串拼模板——四种协议对「系统提示」「工具调用」「流式增量」的表达方式
完全不同。所以中间过一层统一 IR：

```python
{"system": str,
 "messages": [{"role": "user"|"assistant", "parts": [...]}],
 "tools": [{"name", "description", "schema"}], "tool_choice": {...},
 "max_tokens": int, "temperature": float, "top_p": float,
 "stop": [...], "stream": bool}
```

`parts` 四类：`text` / `image` / `tool_use` / `tool_result`。

| 概念 | Chat | Responses | Anthropic | Gemini |
|---|---|---|---|---|
| 系统提示 | `role=system` 消息 | `instructions` | `system` | `systemInstruction` |
| 工具定义 | `tools[].function` | `tools[]` | `tools[].input_schema` | `functionDeclarations` |
| 工具调用 | `tool_calls[]` | `function_call` 项 | `tool_use` 块 | `functionCall` 部件 |
| 工具结果 | `role=tool` 消息 | `function_call_output` 项 | `tool_result` 块 | `functionResponse` 部件 |

**工具 id 严格匹配**是硬骨头：Anthropic 的 `tool_use.id` 与 Chat 的 `tool_calls[].id`
必须一一对应；Gemini 的 `functionCall` 压根没有 id，进 IR 时合成 `call_{name}_{n}`，
出 IR 时按名字反查还原。

#### 16.3 透传优先，字节级原样

**同协议直接透传**：只改 `model` 与认证头，其余字节不动。流式响应**直接把上游原始
SSE 字节转发出去，绝不解析再序列化**——解析再序列化会把上游的私有扩展字段、心跳、
注释行全弄丢。

跨协议才走 IR，且流式场景按**事件**重组（Anthropic 的 `input_json_delta` 聚合成
Chat 的 `arguments` 增量），而不是等整段结束再拼。

#### 16.4 大请求体与内存保护（模块的核心约束）

手机内存紧张，这一节决定了整个模块的形态。

**禁止一次性读取请求体**：代码里没有 `await request.body()`，也没有 `request.json()`。
透传路径用「探针解析」：

1. 从请求流读前 4KB，够从中正则捞出 `"model"` 和 `"stream"`
2. 这 4KB 暂存，把 `model` 就地替换成上游模型名
3. 构造生成器：先 yield 替换后的 4KB，再 yield 剩余部分
4. 生成器直接当请求体交给 HTTP 客户端，**零拷贝、零整包拼接**

实测 20MB Base64 图片透传，进程 RSS 只涨 **0.76MB**（31.9MB → 32.7MB）。

跨协议转换没法零拷贝（必须反序列化），所以另设更严的上限：

| 场景 | 上限 | 超了返回 |
|---|---|---|
| 同协议透传 | 50MB（`max_body_mb` 可调） | 413 `请求体超过 50MB 上限` |
| 跨协议转换 | 10MB（`cross_max_mb` 可调） | 413 `跨协议转换暂不支持超大请求体` |

另外：上传阶段取消写超时；监听客户端断开，前端一断立刻 `shutdown()` 关上游连接；
捕获 `MemoryError` 返回 **507** 而不是让进程崩掉。

#### 16.5 明确不做

基于日志 / 终端 / 文件的场景化 AI 解析、配置自动生成、计费与余额扣费、
向量库、会话记忆、提示词管理、自动重试上游（避免重复扣费）。

#### 16.6 关键实现取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| FastAPI/httpx vs 标准库 | 标准库自实现 | Termux 装不动这两个依赖，硬约束是后端零第三方依赖 |
| 同协议怎么转发 | 字节级透传，只改 model | 解析再序列化会丢上游私有字段；改 model 是唯一必须动的地方 |
| 跨协议怎么转换 | 统一 IR 中间表示 | 四协议对系统提示 / 工具调用 / 流式增量的表达方式全不一样，拼字符串不可维护 |
| 工具 id 怎么对齐 | IR 里按 id 建映射 | Anthropic 的 `tool_use.id` 是多轮工具调用的唯一锚点 |
| Gemini 没有工具 id 怎么办 | 进 IR 时合成 `call_{name}_{n}`，出 IR 按名字反查 | 官方格式如此，只能自己补；同名工具并行调用时可能错位（已知边界） |
| 请求体怎么读 | 4KB 探针 + 生成器直传 | 20MB 图片只涨 0.76MB 内存；`await body()` 会涨 40MB+ |
| 超大请求体怎么拒 | 透传 50MB / 转换 10MB 双上限 | 转换要完整反序列化，内存代价是透传的几十倍 |
| 加密用什么 | HMAC-CTR + Encrypt-then-MAC，不用 AES | AES 引入 `cryptography` 依赖，Termux 装不上；HMAC-SHA256 派生子密钥够用 |
| 丢了 `secret.key` 怎么办 | 旧 Key 解不开，不静默重建 | 静默重建 = 所有 Key 变成乱码但用户以为还能用，比报错更糟 |
| 客户端断开怎么感知 | `select` + `MSG_PEEK` 判断开后 `shutdown` 上游 | 前端关页面后上游还在烧 token；`http.client` 没有 async 的 `is_disconnected` |
| 写超时要不要 | 上传阶段取消 | 大文件传到一半被判超时是假失败 |
| 网关要不要重试上游 | 不重试 | 上游可能已经扣费了，重试等于重复扣费 |
| 路由怎么选 Provider | 精确模型名 > `*` 兜底 > fallback | 兜底 Provider 不该抢走精确匹配的模型 |
| 超限时怎么回 413 | 先读掉剩余请求体，再发响应 | 客户端还在往里写数据时直接关连接，内核回 RST，客户端缓冲区里已收到的响应内容会一起丢掉——表现是「状态码 413，响应体却是空的」 |
| 只配 `*` 的 Provider 怎么显示 | 登记成 `provider/*` | 不登记的话它在下拉框和模型清单里「隐形」，用户以为没生效 |

#### 16.7 验收

1. 填不同厂商 Key 都能流式对话；
2. `curl /v1/messages`（上游只支持 OpenAI Chat）能转换并返回正确格式，含工具调用；
3. 20MB Base64 图片透传，内存无明显上涨（实测 +0.76MB）；
4. 跨协议 15MB 请求返回 413，不 OOM；
5. 中途取消请求时上游连接被正确关闭（假上游的 `disconnects` 计数递增）；
6. API Key 在数据库、日志、接口响应里都不出现明文；
7. 无 Token 的请求返回 401 且带 `WWW-Authenticate: Bearer`。

**实测记录**（真机：Android aarch64 / Termux / Python 3.14.8 / 可用内存约 2GB）：

| 项 | 结果 |
|---|---|
| 单元测试 | 95 项全绿（`tests/test_gateway.py`） |
| 端到端测试 | 36 项全绿（`tests/test_gateway_e2e.py`，自起面板 + 假上游） |
| 20MB 图片透传 | 200，耗时 0.17s，RSS 41.7MB → 43.1MB（**+1.3MB**） |
| 15MB 跨协议 | 413 + 完整 JSON 响应体，RSS +628KB |
| 60MB 同协议 | 413 + 完整 JSON 响应体 |
| 中途取消 | 上游 `disconnects` 递增，网关无异常栈 |
| Anthropic→Chat 流式 | `message_start` → `text_delta` → `tool_use` 块 → 两个 `input_json_delta`（`{"city":` / `"杭州"}`，拼接后正好是 `{"city":"杭州"}`）→ `message_delta(stop_reason=tool_use)` → `message_stop` |
| Key 落盘 | SQLite 内无明文，接口只回 `••••••••3456` |

### 9.1 已知问题与对策

下列问题在 Termux 环境的面板类项目中出现频率较高，建议直接写进开发 checklist。

| 问题场景 | 典型现象 | 对策 |
|---|---|---|
| **Android 12+ 子进程限制** | 后台服务成批被杀，日志无异常 | 前台服务 + wake-lock；必要时引导用户用 adb 关闭 phantom process killer |
| **Termux 签名冲突** | Play 版与 F-Droid 版无法共存、`pkg` 报错 | 安装脚本检测包名与签名来源，提示统一来源 |
| **MariaDB 启动失败** | `mysqld` 直接 abort，部分 ROM 必现 | 指定 `--datadir=$PREFIX/var/lib/mysql`，关闭 native AIO，降低 buffer pool |
| **PHP 扩展缺失** | WordPress 报 `gd` / `zip` / `mbstring` 缺失 | 安装前检测扩展，缺失时给出 `pkg install php-gd` 的准确命令 |
| **存储权限未授权** | 文件管理器看不到 `/sdcard` | 引导执行 `termux-setup-storage`，并检测返回码 |
| **绑定低端口失败** | `bind: permission denied` | 严格限制端口池 ≥1024，UI 层直接不给选 |
| **时区丢失** | cron 在错误时间执行 | 启动时读系统时区并写入 `TZ`，cron 任务显式带 `TZ=Asia/Shanghai` |
| **息屏断网** | 站点从外部不可访问 | 引导关闭 WiFi 省电、保持唤醒；DDNS 心跳检测 |
| **HTTP-01 无法验证** | acme.sh 卡在 80 端口 | 默认走 DNS-01，内置 Cloudflare / DNSPod / 阿里云 API 配置 |
| **LMK 杀进程** | 面板或数据库突然消失 | 内存水位告警 + 服务按需启停 + 降低并发 worker |
| **SQLite 损坏** | 断电后数据库打不开 | WAL + `synchronous=NORMAL` + 启动完整性检查 + 每日备份 |
| **热降频** | 一切正常但响应很慢 | 读取 thermal zone，UI 明确提示「设备过热降频」而不是误报故障 |

### 12.3 主题系统

三态：**浅色 / 深色 / 跟随系统**。默认深色，选择写入 `localStorage`；选择「跟随系统」时监听 `prefers-color-scheme`，系统切换即时生效。

变量分九组：背景、卡片（三级）、边框（两级）、文字（三级）、品牌色、语义色（成功/警告/危险/紫）、阴影（两级）、半透明背景（顶栏/底栏）、代码块。

三条约束：

1. **图表配色随主题走**。浅色下用更深的蓝 `#2563eb`、青 `#0891b2`、橙 `#b45309`，保证白底上的线条对比度；深色下沿用亮色系。
2. **代码块与终端固定深色**。不随主题反转——终端语义本就如此，且语法高亮的亮色在浅底上会失效。
3. **半透明表面用变量而非实时混色**。`color-mix` 在旧内核不可用，顶栏/底栏改为预定义的 `rgba` 变量。

### 12.5 剪贴板适配（WebView 重点）

面板通常跑在 `http://192.168.x.x:8888`，**不是安全上下文**，此时 `navigator.clipboard` 在多数 WebView 中直接不可用。更隐蔽的是：某些内核里它存在，但 `writeText()` 静默 reject。

三级策略：

| 顺序 | 条件 | 行为 |
|---|---|---|
| 1 | `isSecureContext` 且 `navigator.clipboard.writeText` 存在 | 异步写入，成功提示 |
| 2 | 非安全上下文 / WebView | **同步** `execCommand('copy')` |
| 3 | 前两步都失败 | 弹出手动复制面板，文本已全选，长按复制 |

三条实现约束：

1. **降级必须在同一次用户手势内完成**。`writeText()` 是异步的，`await` 之后再调 `execCommand` 已经脱离了手势栈，WebView 会返回 `false`。所以顺序是「安全上下文优先异步，其余直接同步」，而不是「先异步，失败再降级」。
2. **临时 textarea 的写法**：必须 `readonly` + `select()` + `setSelectionRange(0, len)`；隐藏用 `position:fixed; opacity:0`，不能用 `display:none`（无法选中）。
3. **失败不能静默**。原实现在 `catch` 里什么都不做，用户看到「已复制」的提示但剪贴板是空的。现在失败会直接打开手动面板，并说明原因。

手动面板本身也是兜底的一部分：文本框自动全选、提供「重新全选」按钮、显示字符数，适配不同 WebView 的长按菜单差异。

### 13.2 设备适配矩阵（实测结论）

Android 10 对普通应用的限制，使设计阶段的多个常规方案在真机上不可用。以下均为实测，不是推测。

| 设计假设 | 真机结果 | 现方案 |
|---|---|---|
| 读 `/proc/stat` 算 CPU | Permission denied | 解析 `top` 进程行的 `%CPU` 求和，除以核数 |
| 读 `/proc/loadavg` | Permission denied | 不显示负载，改显示运行/总进程数 |
| 读 `/sys/class/thermal` | Permission denied | `termux-battery-status` 的电池温度 |
| 读 `/sys/class/power_supply` | Permission denied | `termux-battery-status` |
| 读 `/proc/uptime` | Permission denied | 显示面板自身运行时长 |
| `syscall.Statfs` 取磁盘 | 进程 SIGSEGV | `df -k` 解析，缓存 30 秒 |
| `ss` 列监听端口 | 命令不存在 | 本地端口 TCP 探测 |
| `netstat -tuln` | `no support for AF INET (tcp)` | 同上 |
| `lsof -i` | 空输出（无权限） | 同上 |

### 13.3 与设计的偏差

1. **端口管理从「监听列表」改为「可连性探测」。** 设计文档原写 `ss -tulpn`，真机上 `ss` 不存在、`netstat` 不支持 AF INET、`/proc/net` 不可读。三者都不可用时，唯一能反映真实状态的信号是「我能不能连上这个端口」。代价是看不到「哪个进程占用的」，换来的是在无 root 环境下仍然可用。

2. **CPU 使用率的分母是物理核数，不是 Go 可用核数。** 设备 8 核，但 Termux 的 cpuset 只给 2 核（`nproc` 返回 2）。CPU 卡片显示 8 核占比，设备卡片另列「Go 可用核心 2 / 8」。这样既不会把 2 线程跑满误报成 100%，也说明了面板自身的调度上限。

3. **`top` 的汇总行不可信。** toybox 的 `800%cpu ... 800%idle` 中 idle 恒为满值（因读不到 `/proc/stat`），但进程行的 `%CPU` 是真实采样值。因此采样逻辑汇总进程行而非汇总行。

4. **进入页面即拉取，不依赖轮询。** 早期实现只在 3 秒轮询里刷新概览，登录后会出现 2–3 秒空白。改为 `go('overview')` 时立即请求。

5. **终端从「WebSocket + tmux」改为「手写 WebSocket + 长轮询双通道」。** 不用 tmux：环形缓冲 + 字节序号已经覆盖「切后台回来接着看」，不需要额外进程。WebSocket 用 200 行手写 RFC 6455 而不是引 `websockets`——同步多线程服务器上引异步库，桥接层比协议实现还长；长轮询保留为不支持 WS 的浏览器与吞 `Upgrade` 的代理的兜底，两条通道共用 `seq` 可无缝切换。

6. **`SIG_IGN` 会跨 exec 遗传，Ctrl+C 全废。** 这是整个终端里最难查的一个问题：
   runsv 按惯例把被管进程的 `SIGINT`/`SIGQUIT` 设为忽略，`exec` 保留这个处置，
   于是面板 fork 出去的 bash、bash 再 fork 的 `sleep` 全都"忽略 Ctrl+C"——
   按 ^C 只回显一个 `^C`，前台进程纹丝不动，`kill -INT` 也杀不掉。
   修法：面板启动时把自身 `SIGINT`/`SIGQUIT` 复位为 `SIG_DFL`，
   并在 `pty.fork()` 的子进程里再兜一次（含 `SIGTERM`/`SIGHUP`/`SIGPIPE`）。

7. **输入必须串行发送。** 每个按键一个 POST 时，几十个并发请求到达顺序不保证，
   服务端拿到的字节序是乱的（实测粘贴一条命令只剩首字母）。
   前端改为串行队列：发送期间新输入先攒着，一次请求带一批。

8. **`sv restart` 会留下孤儿 shell。** `SIGTERM` 默认终止 Python，PTY master 关闭后
   login shell 往往不理会 `SIGHUP`，攒下一堆几 MB 的后台 bash。
   现在 `SIGTERM`/`SIGHUP` 有 handler，先 `close_all()`（SIGHUP → 150ms → SIGKILL 进程组）再退出。
